#### 🧭 Sunday Add-On: Context Lifecycle & the Runtime Connection (30 min)

This is the single most important conceptual note in Phase 2. Write it once, reuse it for the rest of the program.

**1. The context lifecycle — the loop a runtime runs on every turn:**

```
  assemble  →  use  →  observe  →  compact  →  persist
     ↑                                            │
     └──────────── next turn ────────────────┘
```

**2. Context vs Memory vs State — the distinction that separates reliable agents from fragile ones:**

| | **Context** | **Memory** | **State** |
|---|---|---|---|
| What it is | What the model sees *this turn* | What the agent can *recall* | What the agent *is currently doing* |
| Lifetime | Ephemeral (one turn) | Long-lived, retrievable | Durable across the whole task |
| Storage | Assembled in RAM, thrown away | Vector store / document store | Transactional store (DB, checkpoint) |
| Shape | Unstructured tokens | Semi-structured, semantic | **Structured and typed** |
| Correctness risk | Wrong tokens → bad answer | Wrong recall → bad answer | Wrong state → **corrupt execution** |
| Recovery | Re-assemble it | Re-query it | Restore from checkpoint |

> ❌ **The #1 architecture mistake:** treating all three as "memory" and dumping it all in a vector store.
> ✅ **The correct model:** state is *structured and checkpointed*, memory is *retrievable*, context is *assembled per turn from both*.

**3. Short-term vs durable state:** short-term = current turn's scratchpad, plan, tool results.
Durable = task identity, approved steps, completed work, checkpoints. Only durable state survives a crash.

**4. Why this belongs in a runtime, not in a prompt:** budget enforcement, compaction, and state
persistence must happen *on every loop iteration*, must survive restarts, and must be observable.
That is an execution concern — it cannot live in a prompt template.

#### 🧱 Saturday Project: `ContextEngine` (the seed of your Agent Runtime)

Instead of a loose "smart context assembler", build one component with a stable, typed interface:

```python
class ContextEngine:
    def assemble(self, state, query) -> Context      # budget-aware assembly
    def observe(self, context, result) -> None       # record what happened
    def compact(self, state) -> State                # summarize/evict when over budget
    def persist(self, state) -> None                 # durable state — survives restart
```

**Design rules (these are the architecture lesson, not the code):**
- `State` is a **typed Pydantic model**, not a dict, and not a list of messages.
- `assemble()` must **never** silently exceed the budget — it evicts by declared priority and reports what it dropped.
- `persist()` writes to SQLite/JSON so the state can be reloaded after a crash — this is your first checkpoint.
- Every method returns *what it did*, so it can be traced later (Week 14).

📌 **Keep this module.** In Week 12 you will wrap a loop around it and it becomes an Agent Runtime.

#### 🎯 The Definition You Must Own

> **An Agent Runtime is the execution environment that turns a model into a reliable, stateful,
> observable, recoverable worker.**
>
> It answers exactly one question: **"How does an individual agent actually execute reliably?"**

#### 🧭 Responsibilities and Boundaries (framework-neutral)

| Element | Responsibility | Boundary / interaction |
|---|---|---|
| Agent model | Represents the model's capabilities and invocation contract. | Produces proposals or outputs; it does not own authorization or execute tools. |
| Agent framework | Supplies reusable abstractions for graphs, loops, tools, or state. | Optional implementation choice; it may run inside or call a runtime. |
| Agent runtime | Owns one run's lifecycle, state transitions, budgets, cancellation, recovery, and telemetry. | Calls the model and authorized capabilities; does not decide organization-wide policy. |
| Agent harness | Trusted enforcement wrapper around model/runtime inputs and outputs. | Validates identity, tools, schemas, quotas, secrets, and isolation before effects. |
| Tool execution environment | Runs an approved tool/process under filesystem, network, process, and resource limits. | Cannot expand its own permissions or access host resources by default. |
| Orchestration layer | Coordinates workflows, agents, queues, and cross-run dependencies. | Schedules work; each runtime still enforces per-run policy and isolation. |

Define interfaces for run start, state load/save, model invocation, tool
authorization/execution, approval, cancellation, timeout, and terminal result.
Draw one lifecycle from authenticated request through execution to complete,
failed, cancelled, or timed-out; identify which component owns each transition
and what is persisted or traced.

An LLM + a tool loop is a *demo*. A runtime is what makes it a *system*:

```
        Demo                         Runtime
  ─────────────────────      ────────────────────────────────
  while True: call_llm()  →  bounded loop with a budget
  messages = [...]        →  typed, checkpointed state
  tool(args)              →  authorized, sandboxed, traced invocation
  crash = start over      →  resume from last checkpoint
  "it worked on my run"   →  traces, metrics, replayable history
```

#### 🔐 Harness Invariants and Isolation Tests

Write the invariant and its observable test before implementing each boundary:

- The model cannot access host files or write outside an explicitly mounted
  scratch area; access is least-privilege and read-only unless a test requires
  a narrower write path.

  CPU/memory/time, and a termination path that contains descendants.
- Network egress is denied by default; only explicitly approved destinations
  and protocols are reachable.

  check; prompt text, tool descriptions, and generated arguments cannot grant
  permission or bypass approval.

  cross-agent data is unavailable unless an explicit authorized interface
  returns it.

  scoped, brokered outside model context, revocable, and never forwarded as
  unrestricted bearer tokens.
- Dependencies and executable artifacts are pinned/reviewed with provenance;
  resource quotas and timeout/cancellation behavior are tested.

effect did not occur. Include untrusted prompt content and a forged/model-

> ⚠️ **Idempotency is the one most people miss.** Resume replays the last step. If that step charged a card or
> created a work item, you have a bug that only appears in production. Design it now.

#### 🔐 Pillar 2 — Security

```
  Agent Identity      who is this agent? (not "who is the user")
        ↓
  Capabilities        what is it declared able to do?
        ↓
  Tool Authorization  is THIS tool allowed for THIS agent, THIS tenant, THIS request?
        ↓
  Least Privilege     smallest scope, shortest lifetime, narrowest data
        ↓
  Sandbox Isolation   what happens when the tool is hostile or the model is manipulated?
        ↓
  Human Approval      the last line of defence for irreversible actions
```

**Delegated identity lab (required):** define a trusted identity envelope
carrying the authenticated user principal and distinct agent principal,
tenant, audience, scopes, expiry, and delegation chain. Prototype an
authorization decision using a short-lived scoped credential issued through a
broker or token-exchange adapter. Test scope reduction, audience validation,
expiry, revocation, audit correlation, and denial when identity cannot be
resolved. Never let an agent inherit all of the user's permissions or place
credentials in prompts, context, traces, or model-visible tool arguments.

**Agent & MCP threat model (Saturday — this is the highest-value security content in the program):**

| Threat | What it looks like | Runtime mitigation |
|---|---|---|
| Prompt injection | Retrieved doc/tool output hijacks the agent | Treat **all** tool/retrieval output as untrusted; never let it grant privileges |
| Tool poisoning | A malicious/compromised tool description manipulates selection | Pin & review tool definitions; alert on change |
| Confused deputy | Agent uses *its* privileges for the *user's* unauthorized request | Authorize on the **user+agent pair**, not the agent alone |
| Token passthrough | Upstream token forwarded to a downstream tool | Never pass tokens through; mint scoped, short-lived credentials |
| Data exfiltration | Agent sends sensitive data to an external tool | Egress policy + output classification + tool allow-lists |
| Cross-agent trust | Agent B blindly trusts Agent A's output | Verify identity + treat peer output as untrusted input |
| Runaway execution | Loops/subagents burn budget or take real actions | Hard budgets + approval gates on irreversible actions |

> 🧭 **Design principle:** you cannot reliably *prevent* prompt injection.
> You architect so that a successful injection **cannot do anything damaging** — that is a permissions
> and sandboxing problem, not a prompting problem.

#### 🧭 Thursday: Subagent Boundaries

A subagent is a **new execution scope**, not a function call. Decide up front:

- Who pays for its tokens, and against whose budget?
- Can it spawn its own subagents? *(cap the depth, or you get a fork bomb with a credit card)*

- MCP host/client/server roles; tools, resources, prompts; `server/discover`,
  request capability contracts, protocol-version negotiation, typed results,
  error behavior, and cancellation.
- Current standard transports are stdio and Streamable HTTP. The 2026-07-28
  specification is stateless: do not build a dependency on initialization
  handshakes or connection-scoped `Mcp-Session-Id`. The official deprecated
  registry lists legacy HTTP+SSE as deprecated since `2025-03-26`, with
  Streamable HTTP as its migration path; do not adopt it.

  (CIMD) or pre-registration as appropriate. Dynamic Client Registration is
  deprecated for new implementations, migrates to CIMD, and the registry
  lists its earliest removal as the first revision released on or after

  deprecation window unless an approved expedited security removal applies.
- The deprecated registry also lists Roots, Sampling, and Logging as
  deprecated in `2026-07-28`; review its individual migration paths and dates
  rather than treating deprecated features as stable requirements.
- Distinguish core stable protocol behavior from extensions. The official
  extension index currently labels MCP Apps stable, MCP Tasks beta (destination
  Core), Skills over MCP beta (destination not stated), and Server Cards beta
  (destination not stated). Treat experimental extensions as opt-in,
  version-pinned experiments only. The official extension index does not list
  a stable general file-transfer extension; do not make file transfer a
  dependency without a newly verified specification and concrete need.
- A2A agent discovery/cards, messages, tasks and terminal states, delegation,
  identity/authentication, concurrency, and how exchanged outputs remain
  untrusted at the receiving runtime boundary.

#### 🧭 The Boundary (the thing you will be asked in every architecture interview)

| | **Control Plane** | **Runtime (Data Plane)** |
|---|---|---|
| Decides | *whether* something may happen | *how* it happens |
| Frequency | Rarely (config-time, policy-time) | Constantly (every step) |
| If it's down | New/changed agents can't deploy; **running agents keep working** | Work stops |
| Latency budget | Seconds are fine | Milliseconds matter |
| Scope | Org / tenant / fleet | Request / session |
| Examples | registry, policy, catalog, budgets, eval gates | loop, context, tools, checkpoints |

> 📌 **Design rule: the control plane must fail *open* for already-authorized running work, and fail *closed*
> for new authority.** If the registry is down, running agents finish; nothing new gets deployed or granted.

The control plane owns shared configuration and authority decisions through
versioned APIs: agent registration and lifecycle transitions, identity/scopes,
policy bundles, capability discovery, routing/configuration, revocation, and
audit. The runtime owns per-run state transitions and execution. Specify the
API and cache/version contract between them; do not move tool execution,
checkpointing, or per-run isolation into the control plane.

#### 📜 Tuesday: Policy Enforcement Points

You already built a PEP in Week 19. Now place all of them:

```
PEP 1  agent deployment    may this agent exist in this environment?
PEP 2  session start       may this user invoke this agent?
PEP 3  model invocation    may this agent use this model? (cost/data class)

PEP 6  action approval     does this action require a human?               ← ADR-04
PEP 7  egress              may this data leave this boundary?
```
**Policy-as-code** matters because policy must be reviewable, versioned, testable and auditable —
the same reasons you version infrastructure. Policy buried in Python `if` statements is not governable.

#### 🧪 Evaluating Agents Is Not Evaluating Answers

| Layer | What you measure | Example |
|---|---|---|
| **Output** | Is the final answer right? | faithfulness, relevance, format validity |
| **Tool use** | Did it call the right tool, with the right args? | tool precision, arg validity, unnecessary calls |
| **Trajectory** | Was the *path* sensible? | steps taken, loops, redundant work, recovery quality |
| **Cost/latency** | Was it economical? | tokens, $, wall-clock, p95 |
| **Safety** | Did it stay in bounds? | denied-call attempts, injection containment, approval compliance |

> 🧭 **Trajectory evaluation is the agent-specific skill.** An agent can produce a correct answer through a
> path that is expensive, unsafe, or non-reproducible. Outcome-only evaluation hides that entirely.

#### 🚦 Quality Gates (how evaluation becomes governance)

```
agent change → run golden set → score
                                  │
             ┌────────────────────┼────────────────────┐
             ▼                    ▼                    ▼
        score ≥ baseline    regression detected    safety failure
             │                    │                    │
          PROMOTE               BLOCK              BLOCK + alert
```
This is exactly the evaluation gate you implemented in Week 22 — here you learn what belongs inside it.

#### 💰 Cost as a First-Class Control-Plane Capability

```
Token cost  +  Tool cost  →  attributed to  →  agent → tenant → business owner
                                  │
                    enforced by   ├─ per-agent budgets
                                  ├─ per-tenant quotas
                                  ├─ rate limits
                                  └─ model routing (cheap model unless justified)
```
> Untracked agent spend is the #1 reason enterprise agent programmes get paused.
> Cost attribution is **not** a finance concern — it is an architecture requirement.
