#### 🧭 Sunday Add-On: Context Lifecycle & the Runtime Connection (30 min)

This is the single most important conceptual note in Phase 2. Write it once, reuse it for the rest of the program.

**1. The context lifecycle — the loop a runtime runs on every turn:**

```
  assemble  →  use  →  observe  →  compact  →  persist
     ↑                                            │
     └──────────── next turn ────────────────┘
```

**2. Context vs Memory vs State — the distinction that separates reliable agents from fragile ones:**

| | **Context** | **Memory** | **State** |
|---|---|---|---|
| What it is | What the model sees *this turn* | What the agent can *recall* | What the agent *is currently doing* |
| Lifetime | Ephemeral (one turn) | Long-lived, retrievable | Durable across the whole task |
| Storage | Assembled in RAM, thrown away | Vector store / document store | Transactional store (DB, checkpoint) |
| Shape | Unstructured tokens | Semi-structured, semantic | **Structured and typed** |
| Correctness risk | Wrong tokens → bad answer | Wrong recall → bad answer | Wrong state → **corrupt execution** |
| Recovery | Re-assemble it | Re-query it | Restore from checkpoint |

> ❌ **The #1 architecture mistake:** treating all three as "memory" and dumping it all in a vector store.
> ✅ **The correct model:** state is *structured and checkpointed*, memory is *retrievable*, context is *assembled per turn from both*.

**3. Short-term vs durable state:** short-term = current turn's scratchpad, plan, tool results.
Durable = task identity, approved steps, completed work, checkpoints. Only durable state survives a crash.

**4. Why this belongs in a runtime, not in a prompt:** budget enforcement, compaction, and state
persistence must happen *on every loop iteration*, must survive restarts, and must be observable.
That is an execution concern — it cannot live in a prompt template.

#### 🧱 Saturday Project: `ContextEngine` (the seed of your Agent Runtime)

Instead of a loose "smart context assembler", build one component with a stable, typed interface:

```python
class ContextEngine:
    def assemble(self, state, query) -> Context      # budget-aware assembly
    def observe(self, context, result) -> None       # record what happened
    def compact(self, state) -> State                # summarize/evict when over budget
    def persist(self, state) -> None                 # durable state — survives restart
```

**Design rules (these are the architecture lesson, not the code):**
- `State` is a **typed Pydantic model**, not a dict, and not a list of messages.
- `assemble()` must **never** silently exceed the budget — it evicts by declared priority and reports what it dropped.
- `persist()` writes to SQLite/JSON so the state can be reloaded after a crash — this is your first checkpoint.
- Every method returns *what it did*, so it can be traced later (Week 14).

📌 **Keep this module.** In Week 12 you will wrap a loop around it and it becomes an Agent Runtime.

#### 🎯 The Definition You Must Own

> **An Agent Runtime is the execution environment that turns a model into a reliable, stateful,
> observable, recoverable worker.**
>
> It answers exactly one question: **"How does an individual agent actually execute reliably?"**

An LLM + a tool loop is a *demo*. A runtime is what makes it a *system*:

```
        Demo                         Runtime
  ─────────────────────      ────────────────────────────────

  "it worked on my run"   →  traces, metrics, replayable history
```

#### 🛡️ Pillar 1 — Reliability

| Concern | Pattern | Where it lives in your runtime |
|---|---|---|
| Transient model/tool failure | Retry with exponential backoff + jitter | Tool execution, model invocation |
| Hanging dependency | Timeout at every external boundary | Tool execution, model invocation |
| Repeatedly failing dependency | Circuit breaker | Tool registry |
| Duplicate execution on resume | **Idempotency keys** | State update |
| Crash mid-task | Checkpoint + resume | State store |
| Some tools succeeded, some failed | Partial-failure semantics | Observation |
| Invalid/unreadable state | State versioning + validation on load | State store |
| Task runs for hours/days | Durable execution, pause/resume, heartbeats | Session manager |

> ⚠️ **Idempotency is the one most people miss.** Resume replays the last step. If that step charged a card or
> created a work item, you have a bug that only appears in production. Design it now.

#### 🔐 Pillar 2 — Security

```
  Agent Identity      who is this agent? (not "who is the user")
        ↓
  Capabilities        what is it declared able to do?
        ↓
  Tool Authorization  is THIS tool allowed for THIS agent, THIS tenant, THIS request?
        ↓
  Least Privilege     smallest scope, shortest lifetime, narrowest data
        ↓
  Sandbox Isolation   what happens when the tool is hostile or the model is manipulated?
        ↓
  Human Approval      the last line of defence for irreversible actions
```

**Agent & MCP threat model (Saturday — this is the highest-value security content in the program):**

| Threat | What it looks like | Runtime mitigation |
|---|---|---|
| Prompt injection | Retrieved doc/tool output hijacks the agent | Treat **all** tool/retrieval output as untrusted; never let it grant privileges |
| Tool poisoning | A malicious/compromised tool description manipulates selection | Pin & review tool definitions; alert on change |
| Confused deputy | Agent uses *its* privileges for the *user's* unauthorized request | Authorize on the **user+agent pair**, not the agent alone |
| Token passthrough | Upstream token forwarded to a downstream tool | Never pass tokens through; mint scoped, short-lived credentials |
| Data exfiltration | Agent sends sensitive data to an external tool | Egress policy + output classification + tool allow-lists |
| Cross-agent trust | Agent B blindly trusts Agent A's output | Verify identity + treat peer output as untrusted input |
| Runaway execution | Loops/subagents burn budget or take real actions | Hard budgets + approval gates on irreversible actions |

> 🧭 **Design principle:** you cannot reliably *prevent* prompt injection.
> You architect so that a successful injection **cannot do anything damaging** — that is a permissions
> and sandboxing problem, not a prompting problem.

#### 👁️ Pillar 3 — Observability

Learn the **OpenTelemetry GenAI semantic conventions first**, then pick a backend
(LangSmith / Phoenix / Braintrust are interchangeable implementations — the conventions are the durable skill).

**Minimum viable agent trace:**
```
span: agent.run            session_id, agent_id, tenant, outcome, stop_reason
 ├─ span: context.assemble  tokens_in, sections, evicted
 ├─ span: model.invoke      model, tokens_in/out, latency, cost, retries
 ├─ span: tool.execute      tool, authorized?, latency, outcome, retries
 ├─ span: approval.wait     requested_at, decided_at, decision
 └─ span: state.checkpoint  step, bytes, version
```
Metrics that matter: failure rate · retry rate · approval latency · tokens & cost per run · p95 run duration · loop-cap hits.

#### 🧭 Wednesday: Memory Done Correctly

> ❌ **CHANGE THIS (and why):** "long-term memory = dump everything in a vector store" is a 2023-era default
> and a leading cause of unreliable agents. Semantic recall is *lossy and unordered* — it cannot be the system of
> record for what an agent has done.

| Need | Use | Never use |
|---|---|---|
| "What step am I on? What did I already do?" | **Durable state** (typed, checkpointed) | a vector store |
| "What did we learn about this customer 3 months ago?" | **Retrievable memory** (semantic) | runtime state |
| "What does the model see right now?" | **Assembled context** | either one directly |

#### 🧭 Thursday: Subagent Boundaries

A subagent is a **new execution scope**, not a function call. Decide up front:
- Does it inherit the parent's tool permissions, or get a **narrower** set? *(narrower — always)*
- Does it share state, or get an isolated scope with a returned result? *(isolated by default)*
- Who pays for its tokens, and against whose budget?
- Can it spawn its own subagents? *(cap the depth, or you get a fork bomb with a credit card)*

#### 🧭 Wednesday: MCP vs A2A — The Distinction Architects Get Asked About

| | **MCP** | **A2A** |
|---|---|---|
| Connects | Agent → **tools / data / resources** | Agent → **another agent** |

| You get back | A typed result | A negotiated outcome (possibly partial, possibly a question) |
| Trust model | You authorize the tool | You must **verify the peer** and distrust its output |
| Maturity | De-facto standard, broad adoption | Real and standardizing — **still early** |

#### 🧪 Evaluating Agents Is Not Evaluating Answers

| Layer | What you measure | Example |
|---|---|---|
| **Output** | Is the final answer right? | faithfulness, relevance, format validity |
| **Tool use** | Did it call the right tool, with the right args? | tool precision, arg validity, unnecessary calls |
| **Trajectory** | Was the *path* sensible? | steps taken, loops, redundant work, recovery quality |
| **Cost/latency** | Was it economical? | tokens, $, wall-clock, p95 |
| **Safety** | Did it stay in bounds? | denied-call attempts, injection containment, approval compliance |

> 🧭 **Trajectory evaluation is the agent-specific skill.** An agent can produce a correct answer through a
> path that is expensive, unsafe, or non-reproducible. Outcome-only evaluation hides that entirely.

#### 🚦 Quality Gates (how evaluation becomes governance)

```
agent change → run golden set → score
                                  │
             ┌────────────────────┼────────────────────┐
             ▼                    ▼                    ▼
        score ≥ baseline    regression detected    safety failure
             │                    │                    │
          PROMOTE               BLOCK              BLOCK + alert
```
This is exactly the evaluation gate you implemented in Week 22 — here you learn what belongs inside it.

#### 💰 Cost as a First-Class Control-Plane Capability

```
Token cost  +  Tool cost  →  attributed to  →  agent → tenant → business owner
                                  │
                    enforced by   ├─ per-agent budgets
                                  ├─ per-tenant quotas
                                  ├─ rate limits
                                  └─ model routing (cheap model unless justified)
```
> Untracked agent spend is the #1 reason enterprise agent programmes get paused.
> Cost attribution is **not** a finance concern — it is an architecture requirement.
